# 基准测试与真实世界性能

*第 1 章* 至 *第 3 章* 涵盖了 Codex CLI 是什么、如何运行它以及如何有效地提示它。后续章节演示了工具链的主要特性：`AGENTS.md` 约定、审批与沙箱模型、模型名单以及钩子系统。你已了解该工具在理论上提供的能力。现在迎来更棘手的问题：它到底有多好？

2026 年，每个 AI 实验室的营销文案都以基准测试百分比开篇。这些数字看起来令人印象深刻，直到你弄清它们在衡量什么，以及它们刻意*不*衡量什么。基准测试之所以重要，是因为它们提供了一致、可复现的信号。它们之所以会误导人，是因为一旦成为衡量成功的首要指标，实验室就会为优化指标本身而非底层能力而努力。

本章将为你提供批判性词汇以审慎解读基准测试宣称，提供背景知识以理解 Codex CLI 在当前格局中的定位，并提供一套在自有代码库上运行评估的具体方法论：唯一真正对你团队重要的基准测试。

### 学习目标

你将能够：

1. 解读基准测试宣称，识别决定其能否与其他宣称相比较的变量

2. 基于当前评估数据，针对不同任务类型在 Codex CLI 中选择合适的模型配置

3. 使用 Terminal-Bench 任务格式，设计并运行针对自有代码库的轻量级基准测试套件

### 基准测试格局

三大评测主导了 2026 年初关于 AI 编码智能体的讨论。每项测试衡量不同的能力切片，基准测试的选择往往反映了谁的模型在该测试上表现最佳。

**表 25-1. 三大主流 AI 编码基准测试（2026 年 3 月）**

| **基准测试** | **任务** | **范围** | **抗污染能力** |
| --- | --- | --- | --- |
| SWE-bench Verified | 500 个 Python 任务 | Bug 修复补丁 | 低：已知存在污染担忧 |
| SWE-bench Pro | 1,865 个多语言任务 | 多文件变更 | 高：包含 GPL 和专有代码库 |
| Terminal-Bench 2.0 | 89 个端到端任务 | 完整终端工作流 | 高：Docker 环境，众包构建 |

理解这三者的区别是解读产品发布、大会演讲或供应商对比中引用的任何分数的前提条件。

#### 基准测试演进：编码模型五年进化史

在详细考察每个基准测试之前，回顾模型发展的历程将大有裨益。从 OpenAI 最初的 Codex（2021）到 GPT-5.4（2026）的轨迹，展示了快速提升后随之而来的基准测试饱和模式——这是社区需要更难评测的一个反复出现的信号。

HumanEval 实际上已饱和：每个前沿模型得分均超 90%，剩余差距属于噪声而非信号。社区已主要转向 SWE-bench 和 Terminal-Bench 作为区分度更高的评测。

鉴于污染问题（见下节），前沿模型得分超过 ~60% 的情况应持怀疑态度。进步是真实的，但被夸大了。

o3 从 1,258 跃升至 2,727 Elo，是任何编码基准测试中单代际改进最显著的一次，使该模型跻身人类竞赛程序员的顶尖行列。这种能力转化为算法密集型任务的优势，但无法预测其在 SWE-bench 和 Terminal-Bench 所衡量的多文件工程工作中的表现。

该演进的关键启示：基准测试的改进是真实的，但在任务类型间分布不均。在竞赛编程中占主导地位的模型，可能在真实仓库导航中表现不佳。正如本章后节「数字对你的团队意味着什么」所述，始终将基准测试与你的工作负载相匹配。

### SWE-bench：从金标准到警示录

#### SWE-bench 实际衡量的内容

SWE-bench 由普林斯顿大学创建，旨在评估语言模型解决从 12 个热门 Python 仓库中抽取的真实 GitHub 问题的能力。^([220)] 智能体接收问题描述以及问题提出时对应提交点的仓库快照，必须生成一个补丁。成功与否是二元的：应用补丁，运行现有测试套件，通过或失败，不给予部分分数。




#### SWE-bench：从诊断标准到古德哈特指标

这比早期的基准（如 `HumanEval` 或 `MBPP`）要难得多。^(^²²¹^) 模型必须在陌生的代码库中导航，理解跨文件交互，并生成一个满足由另一位工程师为不同目的编写的测试的补丁。当 SWE-bench 推出时，这些特性使其成为真正的诊断工具。

#### SWE-bench Verified 与污染问题

2024 年 8 月，OpenAI 发布了 **SWE-bench Verified**，这是一个包含 500 个人工验证任务的集合，取自原始的 2,294 个任务。^(^²²²^) 它迅速成为比较智能体的事实标准。分数在 2025 年稳步上升。各厂商竞相冲击排行榜榜首。

随后审计开始了。

到 2026 年初，已发布的审计和厂商对 SWE-bench Verified 的谨慎态度证实了许多人的猜测：前沿模型可以复现 Verified 子集任务的金标准补丁，且一些困难任务的测试因错误的原因而通过。

该基准仍能区分较弱和中等水平的模型，但对于前沿模型 Verified 分数超过约 60% 的情况，请抱以真正的怀疑态度。该数字在衡量某些东西；只是不清楚有多少是真正的推理，有多少是记忆。

这是 **古德哈特定律** 正在实时上演：

> 当一种衡量标准成为目标时，它就不再是一个好的衡量标准。

Verified 一成为主要排行榜指标，实验室就直接针对它进行优化：在类似任务上微调、调整脚手架以适配评估工具，以及将临近基准的代码纳入训练数据。结果是分数不再能在前沿水平上进行有意义的区分。基准本身没有失效；它是被古德哈特化了。

污染问题并非 SWE-bench 独有。`HumanEval` 分数超过 90% 的也应持类似怀疑态度。任何公开存在足够长时间的基准都会成为训练目标。

#### SWE-bench Pro：诚实的度量

**SWE-bench Pro** 旨在解决 Verified 的结构性弱点。差异显著：

1.  1,865 个任务，而非 500 个
2.  多语言范围，不再局限于 Python
3.  平均补丁跨度 107 行、涉及 4.1 个文件，而 Verified 的中位数仅为每个补丁 4 行
4.  任务源自 GPL 许可和专有代码库，为训练数据收录设置了法律障碍
5.  一个仅在 Scale Labs 排行榜可见的私有保留子集，防止脚手架团队针对评估集进行调优

由此产生的分数令人谦卑。**Claude Opus 4.5** 在 Verified 上得分 80.9%，但在 Pro 上仅得 45.9%：同一模型、同一能力，得分约减半。^(^²²³^) 在私有子集上，差距进一步扩大：**Claude Opus 4.1** 从 22.7% 跌至 17.8%，**GPT-5** 从 23.1% 跌至 14.9%。这些下降是目前最清晰的信号，表明 Verified 分数的很大一部分反映的是记忆而非泛化。

具体针对 **Codex CLI**，使用带有 OpenAI 自身智能体脚手架的 `gpt-5.3-codex`，OpenAI 报告其在 SWE-bench Pro（公开集）上得分为 56.8%（撰写当时）。在采用标准化脚手架的 Scale AI SEAL 排行榜上，**GPT-5 (High)** 得分 41.8%，**GPT-5.2 Codex** 得分 41.0%。这 10 到 15 个百分点的差距即为脚手架溢价，将在本章后面的脚手架效应部分讨论。

在比较基准分数时，务必核实该数字来自厂商自有脚手架还是标准化评估工具。对于同一底层模型，厂商报告的分数通常比独立标准化分数高出 4 到 12 个百分点。

### Terminal-Bench 2.0：CLI 优先的基准测试

#### 结构与动机

**Terminal-Bench 2.0** 来自 Laude Institute，采取了不同的方法。^(^²²⁴^) 它不再是针对孤立 Python 仓库的合成补丁，而是在 Docker 容器中运行的 89 个精选端到端任务上评估智能体。每个任务提供一条自然语言指令、一个沙箱环境，以及一个自动验证结果的测试脚本。

任务类别涵盖软件工程、机器学习模型训练、系统管理、安全、数据科学和网络安全。任务由 93 位贡献者众包而来，从 229 份提交中根据质量、难度和抗平凡解法能力筛选出 89 个。

这是最直接锻炼 **Codex CLI** 终端原生架构的基准。任务像真实工作一样：搭建训练流水线、调试故障服务、配置构建系统、在受控环境中利用已知漏洞。Docker 沙箱使污染在结构上更难：当任务是让实时服务正确运行时，你无法通过背补丁来应付。

OpenAI 的 **GPT-5.5** 发布报告称其在 Terminal-Bench 2.0 上得分 82.7%，这是一个厂商自测数字，勉强超过了 Anthropic 的 **Claude Mythos Preview**。^(^²²⁵^) 然而，在独立的 Terminal-Bench 2.0 排行榜上，**Codex CLI + GPT-5.5** 以 82.2% 接近榜首，落后于当前领跑者 **NexAU-AHE + GPT-5.5** 的 84.7%。厂商自报分数与其标准化排行榜名次之间的这种差距，正是本章警示的内容：切勿将自报数字视为排行榜名次。前沿竞争现在以零头之差计算，而非两位数的差距。

模型选择对 CLI 影响巨大，且默认配置可能未针对您运行的任务类型进行优化。将 **Codex CLI** 与当前前沿模型（如 `gpt-5.5`）而非旧款或较小模型搭配，可显著提高解决率。

Terminal-Bench 2.0 是最值得亲自运行的基准。**Harbor** 框架使其可复现，Docker 环境防止跨运行污染，完整运行成本约在 `$1` 到 `$100` 之间（取决于模型定价），低到足以将其作为常规评估步骤。

#### 自行运行 Terminal-Bench

可通过 **Harbor** 框架运行基准。您需要 Python 3.12 或更高版本、Docker，以及您要测试的模型提供商的 API 密钥：

```
##### 安装 Harbor（PyPI 包名为 `harbor`；要求 Python 3.12+）
pip install harbor
##### 在 Codex CLI 上运行 Terminal-Bench 2.0
harbor run --dataset terminal-bench@2.0 \
  --agent codex-cli \
  --model openai/gpt-5.5 \
  --n-concurrent 4
```

**Harbor** 的 CLI 变化很快，因此在开始昂贵的运行前，请检查可用的数据集和过滤标志：

```
harbor datasets list
harbor run --help
```

这会生成结构化结果，您可以跨配置进行差异对比并随时间追踪。练习 3 将演示如何解读 Harbor 输出；目前，关键指标是按任务类别的解决率，而非总分。

#### 脚手架效应

**脚手架**，即处理模型周围记忆管理、工具使用协议和重试逻辑的编排层，其重要性可与底层模型本身媲美。使用 **Claude 4 Sonnet** 的 **Confucius Code Agent** 在 SWE-bench 上达到 74.6%，超过了使用能力更强的 **Claude 4.5 Sonnet** 的 **mini-SWE-Agent** 变体。^(^²²⁶^) 更好的编排弥补并随后超越了整整一代模型的差距。



这直接影响你如何配置 Codex CLI。CLI 的原生子代理支持、`AGENTS.md` 上下文加载和 Hook 系统构成了你的脚手架层。一份编写良好的 `AGENTS.md`，能够界定代码库范围、明确测试运行约定并标记禁区目录，可作为持久上下文供模型在整个会话期间依赖。

一个在会话启动时预加载相关文档或近期 Git 历史记录的 `SessionStart` Hook，提供了将称职的基准测试表现与真实任务完成区分开来的基础信息。

配置 Codex CLI 时，你不仅仅是在选择模型，而是在配置脚手架。基准测试数字展示了上限；而你的 `AGENTS.md` 和 Hook 决定了你在特定工作负载下能离这个上限多近。

### 基准测试数字对你的团队究竟意味着什么

将基准测试分数转化为工具决策，需要供应商营销材料很少提供的校准。

#### 将基准测试与你的工作负载相匹配

最常见的错误是将错误基准测试上的高分视为适配性的证据。在评估任何分数之前，先问问哪个基准测试最贴近你的实际工作。

**表 25-3. 基准测试到工作负载的对齐**

| **你的主要用例** | **最具预测性的基准测试** |
| --- | --- |
| Python 仓库中的 Bug 修复 | SWE-bench Pro（而非 Verified） |
| 终端自动化、DevOps、ML 流水线 | Terminal-Bench 2.0 |
| 多语言、多文件特性开发 | SWE-bench Pro 私有子集 |
| 绿地开发 | 目前尚无基准测试能很好地捕捉此场景 |

如果你的团队主要编写 Rust 微服务，仅针对 Python 的基准测试提供的信号有限。如果你的工作是基础设施自动化，即具有平台工程角色特征的 Shell 脚本编写、服务配置和流水线调试，Terminal-Bench 2.0 是唯一一个类似于你实际工作的已发布基准测试。

#### 考虑脚手架膨胀

任何引用供应商自有脚手架的分数，相比标准化评估会膨胀 4 到 12 分。这不是欺诈：自定义脚手架确实能改进结果。但除非双方使用相同的测试框架进行测量，否则会导致供应商间的对比不可靠。

为了进行公平对比，请优先参考 SWE-bench 任务的 SEAL 排行榜数字，或明确指定了代理框架的 Terminal-Bench 结果。当你看到供应商声称“SWE-bench Pro 上达到 X%”时，你的第一个问题应该是：使用的是哪种脚手架？

#### Codex CLI 内的模型选择

鉴于当前的基准测试数据，Codex CLI 模型选择的实用层级从一个有效的本地默认值开始：

```
##### config.toml — 本地默认模型
model = "gpt-5.5"
```

对于需要规划、计算机使用或持久多会话上下文的广泛代理任务，`gpt-5.5` 是正确的起点。对于专业编码任务，尝试显式使用 `gpt-5.4` 并将其与你自己的基准测试套件进行对比。对于你按 Token 付费进行广泛探索的子代理任务，测试 `gpt-5.4-mini` 作为低成本候选。

Codex 不会根据 `config.toml` 中的 `[model]` 表路由任务类别。当你想要对比配置时，请显式更改模型：

```
codex -m gpt-5.5
codex -m gpt-5.4
codex exec --model gpt-5.4-mini "绘制此仓库地图并识别测试命令"
```

重要的习惯是记录每次基准测试运行所使用的模型，而不是假设 CLI 会根据任务类型推断出正确的模型。

### 运行你自己的基准测试

真正重要的唯一基准测试，是在你的代码库上、针对你的任务、在你的约束下的性能表现。

Terminal-Bench 2.0 的结构为构建你自己的微基准测试提供了有用的模板：

1.  **识别 5 到 10 个有代表性的任务。** 选择涵盖你实际要求 Codex CLI 执行的范围的任务：Bug 修复、特性添加和基础设施变更的组合。避免选择微不足道的简单任务或无限制的开放性任务。

2.  **编写确定性的成功标准。** 每个任务都需要一个测试脚本，能在无人工判断的情况下输出通过或失败。这是基准测试设计中最困难的部分，也是合成基准测试倾向于低估真实世界复杂性的原因：真实任务往往有多种有效解决方案，而可靠的自动化测试要求单一的可验证结果。

3.  **容器化环境。** Docker 环境可防止跨运行污染并使结果可复现。每次运行使用相同的基础镜像；锁定依赖版本。

4.  **针对多种配置运行。** 至少将你当前的模型和 `AGENTS.md` 配置与一种替代方案进行对比。替代方案可能是不同的模型、不同的 `AGENTS.md` 结构或不同的 Hook 集合。

5.  **跟踪成本以及解决率。** 取决于你的吞吐量需求，每个任务花费 `$0.50` 且解决率 80% 的配置，可能优于每个任务花费 `$4.00` 且解决率 85% 的配置。

一个小型的基准测试目录赋予工作可重复的结构：

```
.benchmarks/
  task-001/
    README.md        # 自然语言任务描述
    setup.sh         # 将仓库重置为初始状态
    test.sh          # 成功时退出码 0，失败时退出码 1
    expected.md      # 关于预期行为的备注
  results/
    2026-04-23-gpt-5.5-default.json
```

每次都使用相同的结果字段：

| **任务** | **配置** | **通过/失败** | **轮次** | **Token 数** | **成本** | **备注** |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

SWE-EVO 基准测试（测试现有系统的持续演进而非一次性补丁）显示，GPT-5 搭配 OpenHands 得分 21%，而在 SWE-bench Verified 上得分 65%。^(²²⁷) 在商业和企业代码库上，最好的可用模型得分低于 20%。你的专有代码库很可能比任何已发布的基准测试都更难。为这一现实做准备。

目标不是一个可发布的排行榜数字。而是一个一致、可重复的信号，供你用来做配置决策，并在模型和脚手架演进时跟踪退化。即使只有五个任务的测试套件，也能比任何已发布的基准测试提供更多可操作的数据，因为它衡量的是你实际问题领域的性能。

将你的基准测试任务定义和结果存储在专门的仓库目录中（例如 `.benchmarks/`），与你的 `AGENTS.md` 一起纳入版本控制跟踪。随着时间的推移，当你更新 Codex CLI 配置时，你将能准确地看到性能何时以及为何发生了变化。

### 2026 年 4 月基准测试：CocoaBench、HiL-Bench 和 AAR

2026 年 4 月发布的三项同行评审基准测试通过关注代理*如何失败*而非*做对什么*，更新了评估格局。CocoaBench、HiL-Bench 和 AAR（惊人代理竞赛）研究共同为代理式编码工具提供了首个系统性的故障分类学，其结果挑战了关于代理在何处挣扎的一个普遍假设。

#### 故障分类学

2025 年的主导叙事认为工具使用是主要瓶颈：如果代理无法调用正确的 API 或运行正确的命令，就会失败。这些基准测试推翻了该叙事。汇总所有三项研究的故障分类学揭示了不同的图景：

**表 25-4. 代理故障分类学（2026 年 4 月基准测试）**

| **故障模式** | **故障率** | **基准测试来源** | **启示** |
| --- | --- | --- | --- |
| 导航错误 | 27% 至 52% 的试验 | AAR | 代理迷路的频率远高于误用工具 |
| 多模态组合 | ~55% 的任务失败（45.1% 成功率） | CocoaBench | 组合视觉、搜索和代码的长时程任务依然脆弱 |




#### 基准测试中的关键发现

| 发现 | 影响 | 来源 | 含义 |
| :--- | :--- | :--- | :--- |
| 帮助寻求判断 | 需要升级时损失巨大 | HiL-Bench | 无法判断何时寻求帮助的 Agent 表现急剧下降 |
| 工具使用错误 | 最不常见的故障模式 | AAR, CocoaBench | 目前大多数基准测试的焦点——工具使用，极少成为瓶颈 |

这种反转很明显：**导航，而非工具使用，才是主要的故障模式。** 一旦找到正确的文件，Agent 就能熟练地正确调用工具。它们失败的地方在于到达正确的位置。

#### AAR：37.2% 准确率，导航是瓶颈

AAR 研究评估了在交织工具使用与多步导航的任务上的 Agent，其副标题“强工具使用者，弱导航者”精准概括了结果。[²²⁸] 核心数据令人清醒：最优 Agent 仅达到 37.2% 的准确率，且导航错误占主导，根据任务复杂度不同，占试验总数的 27% 至 52%，远超工具使用错误。AAR 在谜题与检索场景而非源代码仓库中衡量导航，但该模式直接迁移至代码库工作：Agent 一旦到达正确位置便能熟练调用工具，但到达该位置的能力薄弱。

对于 `Codex CLI` 用户，实际启示明确：**提升 Agent 性能的最高回报投资，是改进导航辅助。** `AGENTS.md` 中的文件映射（参见第 4 章）、结构良好的目录布局、显式路由规则，能缩小 Agent 必须导航的搜索空间，直接针对主要故障模式。

#### CocoaBench：多模态组合 55% 失败率

CocoaBench 评估统一 Agent 在单一连贯操作中组合视觉、搜索、代码等多模态的长时程任务能力。[²²⁹] 最优系统成功率仅 45.1%，即约 55% 的任务失败。Agent 能很好地处理单一模态，但难以跨模态保持连贯性。

这与第 7 章所述的上下文窗口饱和模式一致：随着任务跨越更多文件和模态，上下文窗口充斥着模型难以整合的异构内容。

#### HiL-Bench：帮助寻求鸿沟

HiL-Bench（人在回路基准）测量了此前无基准测试过的能力：Agent 关于何时寻求人工帮助的判断力。[²³⁰] 结果严峻。前沿 Agent 在获得完整上下文时能解决复杂任务，但一旦必须自行决定是否升级，没有任何前沿模型能恢复超过完整信息性能的一小部分。瓶颈在于判断，而非能力。这对审批模式设计有直接启示（第 5 章）：在 Suggest、Auto Edit 和 Full Auto 之间的选择，不仅关乎控制权，更关乎赋予 Agent 在识别出不确定性时升级的能力。

#### 新基准对你配置的启示

故障分类法建议三大配置优先级：

1.  **投资导航辅助。** `AGENTS.md` 中的文件映射、显式路由规则、结构良好的仓库布局，直接解决 27% 至 52% 的导航失败率。文件映射模式见第 4 章。
2.  **缩小任务范围。** 约 55% 的多模态组合失败率意味着，宽泛的开放式任务（“重构此模块并更新所有测试和文档”）比分解的子任务更易失败。使用子 Agent（第 11 章）将多模态工作拆解为单模态步骤。
3.  **校准审批模式。** 陡峭的帮助寻求性能损失意味着 Full Auto 模式的代价比你想象的大，并非因为 Agent 做危险的事，而是因为它在本应寻求澄清的任务上盲目推进。

### SlopCodeBench：衡量质量，而非仅完成度

前述基准共享一个盲点：衡量 Agent 是否完成任务，而非生成代码是否优质。2026 年 3 月发布的 SlopCodeBench 直接填补这一空白。[²³¹]

SWE-bench 问“补丁是否通过测试套件？”，Terminal-Bench 问“Agent 是否完成工作流？”，而 SlopCodeBench 问代码在增长过程中是否保持结构良好且可维护。它让 Agent 在不断演进的规格下反复扩展自有早期解决方案，并追踪轨迹级质量信号：冗余度（冗余或重复代码占比）和结构侵蚀（复杂度集中在少数函数中）。

早期结果显示，在任务完成类基准上得分高的 Agent，不一定产出高质量代码。用暴力解法通过测试套件的模型，在 SWE-bench 得高分，在 SlopCodeBench 却得分低。对于以代码库健康而非原始任务吞吐为首要关注的团队，你的模型擅长的基准可能无法预测你真正在意的指标。

对 `Codex CLI` 用户，SlopCodeBench 提示：基于钩子的质量检查（Linter、风格强制、写后分析）即便在任务完成基准改进时仍不可或缺。模型可能解决了问题；关键在于该解决方案是否属于你的代码库。

### 基准测试层级体系

2026 年基准格局形成了一个可靠性层级，按适用于你真实工作负载的程度从低到高排列：

底层是 SWE-bench Verified，仍适用于区分弱模型，但在前沿已失去区分度。再上是 SWE-bench Pro，提供更诚实的多文件、多语言推理度量，其私有子集是目前抗污染能力最强的信号。

Terminal-Bench 2.0 与 Pro 齐头并进，作为最贴近 `Codex CLI` 用户的领域特定基准：原生终端、Docker 沙箱、结构上抗记忆化。顶层是源自你实际工作流的自有基准套件，这是唯一能直接回答你提问的评估。

公开数字是缩小选型范围的起点。自有评估才是最终决策的依据。

#### 代码审查基准与采用数据

两个新数据源补充了任务完成类基准，提供真实采用与审查质量的证据。

**OpenAI 报告的代码审查评估** 定性提醒：即使前沿模型在审查代码时，也会遗漏大量真实缺陷。对使用 `Codex CLI` 内置代码审查技能或 CodeRabbit 插件的团队，这校准了预期：自动化审查是有用的首轮筛查，不能替代人工审查。

#### PRDBench：PRD 到代码的鸿沟

PRDBench 由上海交通大学与美团团队推出（2025 年 10 月发布于 arXiv，2026 年被 AAMAS 接受），测量与现有基准根本不同的能力：从产品需求文档（PRD）构建软件，而非修复现有 Bug 或完成部分实现。[²³²] 核心发现是 PRD 到代码的鸿沟显著大于 Bug 修复鸿沟。撰写时排行榜显示，最强模型仅在 60% 左右，弱模型远低于 30%，因为从规格构建需要架构决策、依赖选择、集成规划，而修复导向基准不测试这些。





##### 面向 Codex CLI 用户的 PRDBench 校准

对于 Codex CLI 用户，PRDBench 对绿地开发任务的预期进行校准。如果您的工作流涉及根据规范生成新服务或功能（这是一种常见的企业模式），PRDBench 的得分比 SWE-bench 更能预测智能体性能。该基准还验证了规范驱动开发方法：提供结构化的 PRD（产品需求文档）而非模糊的提示词，能显著提高解决率。

#### MAESTRO：多智能体评估

MAESTRO（用于测试、可靠性和可观察性的多智能体评估套件）填补了单智能体基准的空白：评估多智能体系统中的编排质量。[²³³] 其关键发现在于，架构选择——智能体如何组合、共享何种状态以及故障如何传播——对多智能体性能的影响大于模型选择。一个编排良好的系统即便使用较弱的模型，也能胜过编排不善但使用更强模型的系统。

这一发现强化了第 12 章中的编排模式：这些模式本身就是性能杠杆，而不仅仅是组织便利。MAESTRO 提供了评估方法论，用以衡量您的编排架构究竟是在提供帮助，还是引入了超出并行化收益的协调开销。

### 基准的另一面：生产环境中的智能体代码质量

迄今讨论的基准衡量的是智能体能否完成任务。2026 年初发布的两份主要行业报告提出了一个不同的问题：智能体写完代码后会发生什么？答案令人警醒，为解读任何基准分数提供了必要的背景。

#### Opsera 与 Sourcery Intel 2026 报告

Opsera《AI 编码影响 2026 基准报告》分析了 60 多家企业、超过 250,000 名开发者的数据。[²³⁴] Sourcery Intel《2026 年 AI 编码智能体现状》综合了整个智能体领域的市场、基准和安全数据。[²³⁵] 两者共同勾勒出一幅关于智能体输出质量一致的图景。

**表 25-5. 智能体代码质量发现（2026 年初）**

| 发现 | 数据 | 来源 |
| --- | --- | --- |
| AI 生成代码漏洞率 | 14.3% 对比 9.1% 人工（相对增加 57%） | Sourcery Intel（斯坦福-MIT 研究，200 万+ 片段） |
| 每行漏洞数 | 比人工代码多 15% 至 18% | Opsera（25 万+ 开发者） |
| 评审队列延迟 | AI 生成的 PR 长 4.6 倍 | Opsera |
| 代码重复率 | 样本中 10.5% 至 13.5% | Opsera |
| PR 时间缩短 | 快 48% 至 58% | Opsera |
| 高级与初级生产力增益差距 | ~5 倍 | Opsera |
| 闲置 AI 编码许可证 | 21% | Opsera |

这种悖论十分显著：AI 辅助工作流将拉取请求的时间缩短了 48% 至 58%，但由此产生的 PR 在评审队列中停留的时间却长了 4.6 倍。代码生产的加速已超过了审查能力。团队产出更多 PR，但评审人员无法跟上，导致未审查的、潜在脆弱代码积压日益增加。

#### PR-MCI：当描述撒谎时

一项被 MSR 2026 接收的研究分析了五个 AI 编码智能体的 23,247 个拉取请求，人工标注了 974 个 PR 以验证自动化的 PR-MCI（PR 消息-代码不一致）检测管道。[²³⁶] 研究结果量化了许多评审人员直观感受到的信任赤字：

1.  1.7% 的智能体 PR 表现出高消息-代码不一致：描述声称的更改在差异中并未实现。
2.  最常见的故障模式（占高 MCI 情况的 45.4%）是“描述声称未实现的更改”。
3.  高 MCI PR 的接受率低 51.7%（28.3% 对比 80.0%）。
4.  它们的合并时间长 3.5 倍（55.8 小时对比 16.0 小时）。

CodeRabbit 对 470 个开源 PR 的分析从另一个角度佐证了这一点：AI 合著的拉取请求包含的问题大约是纯人工 PR 的 1.7 倍（每个 PR 10.83 个问题对比 6.45 个），质量差距跨越逻辑与正确性（1.75 倍）、代码质量（1.64 倍）、安全性（2.74 倍）和可读性（3.0 倍）。[²³⁷]

#### 这对基准解读意味着什么

这些发现并未使基准分数失效。它们为分数提供了背景。在 Terminal-Bench 2.0 上得分 82% 的模型确实有能力完成复杂任务。但它生成的代码可能带有 14.3% 的漏洞率，可能复用现有抽象，且可能附带不能准确反映变更内容的 PR 描述。基准完成是必要条件，但非生产级输出的充分条件。

对 Codex CLI 用户的实际启示：基准分数告诉您哪个模型能解决问题。`PostToolUse` 钩子、自动化评审（`auto_review`）、`AGENTS.md` 质量约束和结构化输出模式（第 9、20、4 和 22 章）告诉您该解决方案是否属于您的代码库。

### 总结

1.  **SWE-bench Verified 在前沿领域已被污染。** 约 60% 以上的分数反映了部分记忆化。SWE-bench Pro 是更诚实的衡量标准，同一模型的得分低 30 至 40 分。
2.  **GPT-5.5 领跑 Terminal-Bench 2.0。** OpenAI 报告得分为 82.7%（供应商自测数据，略微领先 Claude Mythos Preview）；独立排行榜显示 Codex CLI + GPT-5.5 得分 82.2%，仅次于当前 SOTA 的 NexAU-AHE + GPT-5.5（84.7%）。在 SWE-bench Pro 上得分 58.6%，在 SWE-bench 上得分 88.7%。
3.  **Terminal-Bench 2.0 是 Codex CLI 用户最相关的基准。** 它在 Docker 沙盒环境中运行端到端的终端工作流，是终端原生工作最接近的已发布代理指标。
4.  **SlopCodeBench 衡量质量，而不仅是完成度。** 它通过对代码质量（可读性、可维护性、地道风格）评分而非任务是否完成，解决了现有基准的盲区。
5.  **脚手架膨胀增加 4 至 12 分。** 供应商报告的分数高于标准化基线，因此切勿直接将供应商报告的分数与 SEAL 排行榜分数比较。
6.  **模型选择与脚手架同等重要。** 模型升级提高上限；`AGENTS.md`、钩子、审批模式和任务设计决定您的工作流能多接近该上限。
7.  **最好的基准是您自己的代码库。** 以 Terminal-Bench 的任务格式为模板，在版本控制中跟踪结果。
8.  **PRDBench 揭示了 PRD 到代码的鸿沟。** 从规范构建比修复 Bug 困难得多，最强模型得分在 60% 左右，仍远低于其 SWE-bench 表现。（上海交通大学和美团团队；arXiv 2025 年 10 月，AAMAS 2026。）
9.  **对于多智能体工作，编排架构胜过模型选择。** MAESTRO 证明了这一点，验证了第 12 章中涵盖的编排模式投资的价值。
10. **生产代码质量讲述了与完成度不同的故事。** 报告引用了 14.3% 的漏洞率（Sourcery Intel）、4.6 倍的评审队列延迟（Opsera）以及代码重复率从 10.5% 上升至 13.5%。PR-MCI 研究（MSR 2026）显示 1.7% 的智能体 PR 存在误导性描述，接受率低 51.7%，合并时间长 3.5 倍。基准完成是必要条件，但非生产级输出的充分条件。

### 练习





#### 任务与基准测试

#### 1. 审计基准测试声明
寻找某 AI 实验室近期引用代码基准测试分数的新闻稿或博客文章。识别：
- (a) 引用的是哪个基准测试变体
- (b) 使用的脚手架是供应商自有的还是标准化测试框架
- (c) 是否存在同一模型对应的 SEAL 排行榜条目

若两个数字都存在，计算脚手架溢价；若不存在，准确记录缺少哪个对比。最后用两段总结该引用数字实际说明了模型在您工作负载上的可能表现。

#### 2. 构建五任务微基准
从团队近期 Sprint 历史中选取五个具有代表性的真实任务（Issue 或 PR），而非编造场景。使用本章的 `.benchmarks/` 结构。对每个任务：
- 编写确定性成功测试（成功退出码 0、失败退出码 1 的 Shell 脚本）
- 使用 Docker 容器化初始环境
- 用当前配置运行 Codex CLI，记录解决率和单任务成本
- 修改一个变量（模型选择、`AGENTS.md` 内容或 Hook 配置）并重新运行
- 记录哪个配置获胜及原因

#### 3. 对子集运行 Terminal-Bench 2.0
安装 Harbor 框架，运行 `harbor datasets list`，并用 `harbor run --help` 确定当前过滤标志。从与您工作相关的类别中选取 10 到 15 个 Terminal-Bench 2.0 任务，分别对两个 Codex CLI 模型配置 `gpt-5.5` 和 `gpt-5.4` 运行。对比解决率和总成本。若结果与表 25-2 发布的排行榜数字差异显著，分析原因。考虑您的 `AGENTS.md` 配置、网络环境，以及您选取的任务类别是否映射到模型的训练强项。与团队分享发现，并以此作为今后默认模型选择的依据。

#### 4. 在小型项目上运行自有基准
从积压工作中选择一个真实的 Bug 或功能请求（手动耗时 15 到 30 分钟）。将 Issue 文本放入本地基准任务文件，或让提示词明确告诉 Codex 如何获取，例如：
```bash
codex "Fix issue #N. Use gh issue view N to read the issue, then run the project tests."
```
计时结果。记录是否通过测试、轮数和 Token 成本。与本章发布的基准分数对比。记录真实结果偏离实验室结果的位置及原因（代码库复杂度、测试覆盖率、`AGENTS.md` 中的领域知识）。

#### 5. 测量您工作流的脚手架溢价
脚手架溢价是指归因于脚手架（提示词、`AGENTS.md`、Hook、审批模式、任务设计）而非底层模型的性能差异。从积压工作中选取一个代表性任务，每次仅改变一个变量，运行两遍。从相同模型和审批模式开始，先用最小配置，再用生产环境的 `AGENTS.md` 和 Hook。记录输出质量、Token 数和耗时。如需区分脚手架效应与模型效应，可换用不同模型重复。这些数据在评估是否升级模型或投资改进脚手架时极具价值。
