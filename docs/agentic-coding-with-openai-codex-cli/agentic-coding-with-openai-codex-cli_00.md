# 前言

## 这一切始于一列火车上

从 Audley End 到 Liverpool Street 的 07:02 班次需要五十八分钟，除非 Tottenham Hale 出了问题，否则能在 08:00 抵达伦敦。2025 年 11 月的一个周二，我打开笔记本电脑，有一个还算不错的移动数据连接，还有一个模糊的意图：终于要认真对待 Codex CLI 了。我几周前安装过它，运行了几个命令，耸耸肩，然后回去做我原本在做的事了，可能是玩 Gemini Nano Banana 玩得挺开心。那天早上我遇到了一个真实的问题：六个月前写的一个 Node 服务在预发布环境开始表现异常，我以来一直没看过它了。我甚至对这仓库的情况记忆犹新。

我将 Codex CLI 指向项目目录，描述了症状，然后看着它运行。

接下来发生的事情就是你正在读这本书的原因。它不仅仅是建议修复方案。它读取源文件，追踪执行路径，运行测试套件，发现了一个我没提到的第二个问题，为它编写了一个失败的测试，修复了这两个问题，并询问我是否应该打开一个拉取请求。当我们驶入 Tottenham Hale（那里确实出了问题）时，我已经有了一个干净的差异对比、一个关于根本原因的简短解释，还有一种对刚才所见之事的微妙不安感。

我从早期的 Copilot 时代就开始使用 AI 编码助手了。我经历过在浏览器标签页用 ChatGPT、侧边栏用 Claude、各种 Copilot 变体、Cursor、Windsurf，还有一堆我已经忘记名字的其他工具。它们都很有用，就像自动补全有用一样。但这次不一样。并非因为它更“聪明”，确切说不是，而是因为它在**运行**：读取上下文、采取行动、管理状态、从错误中恢复，而不是单纯地响应。这种区别听起来很微妙，但其实不然。

那就是这本书变得必要的时刻。

## 是什么改变了我的想法

改变我想法的不是任何单一的惊艳输出。而是理解了其架构。

大多数 AI 编码工具的核心，都是带有上下文窗口的复杂文本补全器。你给它们代码；它们给你更多代码。质量参差不齐，上下文窗口不断变大，集成越来越顺滑，但底层模式是被动的。你提示，它响应。你接受或拒绝。你再提示。

Codex CLI 建立在不同的前提上。它是一个智能体循环。你给它一个目标，它会规划、执行、观察结果、调整，并持续下去，直到完成或卡住。它拥有真正的工具使用能力：它可以读写文件、运行任意 Shell 命令、执行测试、调用外部 API。它可以生成子智能体并行处理独立的子任务。它在会话内跨步骤保持上下文。它知道何时该请求澄清，何时该自顾自地干下去。

这种架构很重要，因为它改变了工具的适用范围。自动补全擅长逐行编码。聊天擅长问答。智能体执行擅长**任务**——那些有始有终、需要读取多个文件、运行多个命令、在过程中做出多个决策的事情。重构一个模块。端到端地添加一个功能。诊断一个构建失败。这些曾是吞噬你整个下午的事情。这些正是 Codex CLI 专为之而生的。

关于 AI 编码工具的大量惊叹式评论——而且有很多，大多言过其实——都忽略了这一区别。人们对自动补全质量做基准测试，或衡量模型建议正确函数名的频率。这没问题，但衡量的是错东西。有趣的问题不在于模型能否写出排序算法。而在于该工具能否坐在你身边，融入你的实际工作流、你的代码库、你的测试、你的 CI 系统、你的约定，并凭借真正的自主性做出有用的工作。Codex CLI 对该问题的回答，是我见过最有趣的。

本书是我试图解释原因，并教你如何正确使用它的尝试。

## 适读人群

我写这本书是给中高级软件工程师看的，他们已经习惯了 AI 辅助开发，并且在想智能体工具是否会改变局面。如果你用 GitHub Copilot 用了一阵子，或者你已经在用像 Claude Code 这样的智能体工具，你了解这些工具擅长什么、不擅长什么，并且想从智能体方法中榨取更多价值：这本书就是为你写的。




你应该熟悉终端操作。`Codex CLI` 是一个命令行工具，本书将其视为命令行工具对待。没有 GUI，没有插件，没有侧边栏。一切都在你的 Shell 中发生。如果这听起来有吸引力而非惊悚，那你来对地方了。

你不需要深厚的机器学习或大语言模型专业知识。我会解释你有效使用 `Codex CLI` 所需了解的底层模型工作原理，但这不是一本机器学习教科书。我假设的是工程经验：阅读代码库的能力、推理系统行为的能力、在不确定性中调试的能力。这些技能可直接迁移。

本书不适合想了解 AI 全景的管理者，也不适合对软件开发前景好奇的非技术读者。市面上有适合那些受众的好书。本书不是其中之一。我为工程师而写，并力求用工程师觉得有用的具体、明确的方式表达。

还有一点：我是从每天使用该工具的实践者视角写作，跨越企业交付、研究和工程团队。我曾在生产代码库、新建项目、CI 流水线和本地开发中运行 `Codex CLI`。本书中的观点建立在该实践基础上，而非基准测试或演示。

# 你不会在本书中找到的内容

我想诚实地说明本书范围。过度承诺覆盖面的书对读者是一种损害。

**这不是一本通用的提示工程入门书。** 市面上有很多，其中一些很优秀。本书假设你能写出像样的提示，而是专注于适配 `Codex CLI` 代理模式的特定模式和习语。

**这不是一本 LLM 教科书。** 我不会解释注意力机制、Transformer 架构或当前前沿模型的训练方式。在底层模型至关重要的特定场景下，我会解释你需要知道的内容。但理解神经网络并非有效使用 `Codex CLI` 的前提。

**这不是一本市场调研报告。** 我不会花费篇幅对比 `Codex CLI` 与 Cursor、Devin、Aider、Claude Code 及领域内的其他每个工具。那种对比在本书付印前就会过时。我将解释代理方法与替代方案的区别，让你自行判断这对你已在使用的工具有何意义。

你将在这里找到的是：一位作者基于数月的日常使用，深度覆盖单一工具，并对什么有效、什么无效持有强烈观点。

# 本书的组织结构

全书分为六个部分。

**第 1 部分：基础** 将 `Codex CLI` 置于语境中，并确立代理始终读取的持久上下文。它是什么、源自何处、如何安装和提示、什么属于 `AGENTS.md`？如果你完全不熟悉该工具，从这里开始。如果你已使用一段时间，可略读第 1 部分，在相关章节需要时再回来查阅。

**第 2 部分：护栏** 涵盖引导和约束运行的可配置杠杆：审批模式、模型选择、上下文管理、MCP 集成和钩子系统。这是你最常作为参考返回的部分。我力求让各章节独立成章。

**第 3 部分：规模化** 解释如何超越默认设置。技能、子代理、多代理编排、成本管理和 CI/CD 集成。如果你有特定工作流或约束，这部分会变得有趣。

**第 4 部分：生产** 解决从个人使用转向团队使用时出现的问题。安全加固、企业配置、调试和测试策略。

**第 5 部分：实践指南** 是应用篇，包含使用 `Codex CLI` 进行代码审查、代码库迁移、基础设施即代码、前端工程、Python 团队和基于 Worktree 隔离的具体、详细演练。本部分每章都跟踪一个真实任务从开始到结束。

**第 6 部分：大局观** 从个别工作流中抽离，审视架构：基准测试、竞品工具、测试工程和代理工程小组的新兴角色。这些章节假设你已通读前几部分，准备好思考更宏大的图景。

# 关于版本时效性的说明

`Codex CLI` 每周发布，有时更频繁。你今天安装的工具可能与我撰写特定章节时使用的表现不同。这不是不信任本书的理由：架构、心智模型和核心工作流是稳定的。这确实意味着你应将特定标志和配置选项视为起点而非教条。`codex --help` 的输出永远比本书印刷内容更权威。

一个保持跟进的实用建议：阅读变更日志。`Codex CLI` 的变更日志异常优秀，团队对变更内容及原因保持透明。

# 如何使用本书

如果你是首次阅读，我建议从头读到尾，至少读完第 3 部分。本书层层递进：早期引入的概念在后续章节中直接使用而不再重述，第 1 和第 2 部分的心智模型会让第 3 和第 4 部分容易得多。

如果你作为参考书回顾，第 2、3、4 部分的每章都设计为独立成章。索引详尽，我大量交叉引用。你不必重读周边章节即可获取所需信息。

如果你带领团队阅读本书、举办研讨会或让工程师快速上手代理工具，第 5 部分专为此设计。每个实践指南均结构为动手练习。
