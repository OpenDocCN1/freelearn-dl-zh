# 第二十六章：竞品工具及适用场景

第 25 章表明，决定编码代理性能差异的主要是测试框架而非模型：LangChain 在模型不变的情况下将 Terminal-Bench 2.0 排名从第 30 位提升至第 5 位，脚手架溢价可为基准分数增加 4 到 12 分。本章将这一视角转向竞争格局，提供任务决策框架、架构权衡的诚实评估，以及何时不应选择 Codex CLI 的指导。

推荐单一工具对抗固定竞品名单的书籍很快过时，因为名单每季度都在变。等您读到此书时，代理式编码市场已进一步整合，此处提及的部分产品可能已重命名或退市，新产品也会出现。请将文中工具视为架构类别的代表，而非固定清单。类别持久；占据类别的品牌名则不然。本章提及工具时，系作为该类别当前最清晰的示例，而非永久固定。

该领域沿一条架构轴线划分：**CLI 代理**运行在终端、操作文件系统，对比 **IDE 代理**驻留在编辑器、通过可视化 Diff 和内联补全呈现 AI。少数工具跨足两端，但其设计理念通常揭示其优先服务哪一侧。此区分很重要，因为两个层级优化目标不同。终端代理优化无人值守执行、可脚本化、与 CI/CD 流水线集成。IDE 代理优化紧凑反馈循环、可视化 Diff、不离开编辑器的舒适度。为任务选错层级不仅低效，有时在架构上根本不可能。您无法通过 IDE 插件运行内核级沙箱 CI 流水线，也无法从无头终端代理获得内联可视化 Diff。

开始前的一个诚实元观点：若您已从其他工具获得所需结果，可能无需切换。本章旨在帮助您有意识地得出该结论，或识别出 Codex CLI 优势使其成为更好选择的具体场景。

### 测试框架工程视角

一篇 42 位作者的调查论文（“Code as Agent Harness”，arXiv 2605.18747）提供了理解为何使用相同底层模型的工具产出截然不同结果的学术框架。论文指出所有编码代理通用的三层架构：

1.  **接口层**——代理如何接收指令并呈现结果：`AGENTS.md` 文件、系统提示词、终端 UI 对比编辑器面板。
2.  **机制层**——约束与赋能代理行为的要素：Hook、权限配置文件、沙箱、审批模式。
3.  **多代理扩展层**——代理如何协作：子代理、MCP 服务器、交接协议。

关键洞见：模型非差异化因素；测试框架才是。两个运行可比模型的工具因其测试框架在每层做出不同工程选择而产出显著不同结果。一者在机制层投资内核级沙箱和 Token 效率；另一者在接口层投资可编程 Hook 和更丰富的推理展示。模型设定能力上限，但测试框架决定您在真实任务上能触及多少上限。第 27 章将深入展开这一论点；本章将其作为选型视角应用。

### 学习目标

您将能够：

1.  应用决策框架，根据特定任务与约束概况在 Codex CLI 与竞品代理间选择
2.  解释内核级沙箱、可编程 Hook 与 IDE 原生反馈循环的架构权衡
3.  在两个工具上运行同一任务，按成本、质量、人机工效评估结果
4.  设计多工具工作流，让各工具发挥其架构强项
5.  按代理沙箱最弱的强制边界而非最强边界对其分类
6.  将配置、技能、子代理、Hook 从其他代理（如 Claude Code）迁移到 Codex CLI

### 决策框架




诚实的回答是，大多数经验丰富的从业者会使用不止一种工具。问题不在于选哪一个，而在于根据具体任务和约束情况，该拿起哪一个。表 26-1 将常见场景映射到适合的架构类别，并为每个类别列出了代表性工具。

**表 26-1. 何时使用哪种工具**

| **场景** | **首选** | **主要原因** |
| --- | --- | --- |
| 内核级沙箱是硬性要求 | 具有操作系统强制隔离的 CLI 代理 (`Codex CLI`) | 操作系统层面的 Seatbelt/bubblewrap 强制执行，而非应用层策略 |
| 复杂、可编程的合规逻辑 | 具有丰富钩子事件的 CLI 代理 (`Claude Code`) | 策略以程序形式表达，而非配置 |
| 规模化的 Token 高效批处理工作 | 终端优先的 CLI 代理 (`Codex CLI`) | 无头运行避免了 IDE 协议开销 |
| 对全新 Bug 进行最高质量推理 | 运行最强前沿模型的代理 | 在真正的新问题上，模型能力占主导 |
| 代码落地前进行可视化差异对比 | IDE 原生代理 (`Cursor`) | 内联差异审查是原生用户体验 |
| 永不离开编辑器 | IDE 原生代理 (`Cursor`, `GitHub Copilot`) | 无需终端上下文切换 |
| 授权并放手解决 Issue | 异步云代理 (`GitHub Copilot coding agent`) | 在托管沙箱中从 Issue 到 PR，无需本地会话 |
| 厂商中立、模型不可知、物理隔离 | 开源 CLI 代理 (`OpenCode`) | 无厂商锁定；自带模型 |
| 预算是约束性因素 | 免费层级或开源代理 | 零或低边际成本改变使用模式 |
| 具有沙箱化、无人值守执行能力的 CI/CD | 终端优先的 CLI 代理 (`codex exec`) | 可脚本化、内核沙箱化、专为无头使用而构建 |

### CLI 代理

#### Codex CLI 优势

`Codex CLI` 的优势集中在工具链的机制层，这正是调查论文预测持久差异所在的地方。

1.  **内核级沙箱。** 操作系统强制隔离，macOS 上为 Apple Seatbelt，Linux 上为带 seccomp 的 bubblewrap，而非应用层限制。沙箱在系统调用层面运作，因此无论代理被说服尝试何种操作，隔离均有效。*第 16 章* 深入探讨了安全含义。

2.  **Token 效率。** 无头终端操作避免了 IDE 协议层（编辑器状态同步、补全流、UI 更新消息）带来的 Token 开销，而这些是 IDE 耦合代理的额外负担。*第 14 章* 解释了为何该差距在团队规模下成为预算输入项。

3.  **CI/CD 原生。** `codex exec` 运行任务、返回结果并退出：天然适配流水线集成，*第 15 章* 对此进行了详细阐述。

4.  **渐进式审批模型。** 审批系统提供了一系列信任级别，并由内核级强制执行作为后盾，这在架构上区别于二元的基于信任的开关。命名配置文件 (*第 5 章*) 使这些预设可复用且可版本控制。

#### Claude Code：最接近的对标产品

`Claude Code` 是 CLI 代理类别中的主要竞争对手，也是 `Codex CLI` 最接近的对标产品。^(²³⁹) 它是使用最广泛的终端代理之一，当推理质量是约束性因素时，它是一个强有力的选择：在涉及定位和修复微妙 Bug 的多文件任务中，它始终能产出高质量的修复，且在撰写本文时，其公开的 SWE-bench Verified 分数位居前列。（将任何特定基准数据视为快照；实时排行榜才是真理来源。）

有两个架构差异值得理解而非死记硬背。第一是策略表达能力。`Claude Code` 暴露了一组丰富的钩子事件，允许你在 Shell 脚本中编码任意复杂的策略逻辑。钩子是程序，而非配置，因此其表达能力实际上是无限的。`Codex CLI` 的安全模型则倾向于内核级沙箱，这提供了更强的隔离性，但对于定制化的合规工作流灵活性较低。两种方法均无绝对优势：可编程钩子能表达沙箱无法表达的策略，而沙箱能强制执行运行在同一信任域内的钩子无法保证的边界。

第二个差异是强制执行默认值。`Claude Code` 自带操作系统级沙箱（macOS 上为 Seatbelt，Linux 和 WSL2 上为 bubblewrap），用于代理生成的 Shell 子进程，因此区别在于作用范围和默认值，而非强制执行机制的存在与否：该沙箱覆盖 Bash 子进程，而文件读写通过权限层进行；其网络过滤基于主机名且不执行 TLS 检查；且沙箱是可选加入的，而 `Codex CLI` 将内核级隔离视为架构默认。如果你的主要需求是推理质量和可编程策略，`Claude Code` 是绝佳选择；如果是默认的硬隔离和 Token 效率，`Codex CLI` 更具优势。

`Codex CLI` 在直接对比中获胜的往往在于 Token 效率和成本。独立测试反复发现 `Codex CLI` 比 IDE 耦合代理消耗少得多的 Token，在某些 CLI 对 CLI 的对比中，完成同一任务其 Token 消耗甚至比 `Claude Code` 少几倍。^(²⁴⁰) 在个人规模下差异可忽略；在团队规模下，这会转化为成本节约或容量余量，从而成为规划输入项。评估这两者用于特定项目时，实用的做法是在两者中运行相同任务并直接检查 Token 计数，这正是本章第一个练习的主题。

#### Google 的终端代理

Google 在同一类别中推出了一款终端代理，其决定性特性是拥有真正的免费层级和大上下文窗口，这比任何基准测试都更能改变使用模式。^(²⁴¹) 开发者若因每次查询几美分的成本而不愿请教代理快速定向性问题，在零成本下则会乐意提问，因此免费层级将代理变为探索和文档伴侣，而非代码修改主力。它还提供实时网络搜索接地，这对涉及近期库版本或模型训练截止日期后可能已变更的 API 的任务很有用�。

权衡点与该类别一致。其沙箱基于容器而非内核级，且在复杂推理或多文件重构的基准性能上尚未追平前沿 CLI 代理。对于成本非约束性因素且任务质量至上的团队，前沿代理产出更好结果；对于探索、定向和代码库快速问答，免费层级创造了真实价值。撰写本文时，Google 在此领域的产品谱系处于变动中，其终端产品正被整合进更广泛的平台，因此请将品牌名称视为比其所在类别稳定性更低的标识。

#### 开源与厂商中立代理




### 第三方 CLI 代理：开源工具

第三类工具是开源 CLI 代理，如 `OpenCode`、`Aider` 和 `Continue`，它们以生态深度换取供应商独立性。^[²⁴²] `Codex CLI` 与 OpenAI 的模型栈紧密耦合，而这些工具将每个供应商视为一等公民，在一个接口后支持数十个模型后端，通常采用宽松许可证，使其无需采购审查即可嵌入。对于运行本地模型的气隙环境，或采购流程使专有工具变得不切实际的组织，它们完全消除了锁定顾虑。

代价是使商业工具对多开发人员团队具有实用性的那层有观点的配置。这些代理通常缺乏商业选项的内核级沙箱、命名权限配置文件和托管企业功能，且其基准性能往往未经独立验证。当供应商中立性、气隙操作或模型不可知论是主要需求时，它们是强有力的选择；但当你需要开箱即用的团队范围约定和硬隔离时，则较难推销。

### 规格驱动与并行编排代理

还有两类 CLI 值得提及，因为它们代表了真正不同的设计理念，而非增量功能差异。

#### 规格驱动代理

**规格驱动代理** 将结构化规格（而非代码库）视为主要工件。`Codex CLI` 是终端优先且极简的（提示、执行、沙箱），而规格驱动代理首先将自然语言请求转换为代理和人类共同参考的正式规格，然后才生成代码。这适合已从书面规格工作并希望代理计划成为可审查文档的团队；它增加了快速单文件编辑不需要的仪式感。`Codex CLI` 通过手动规划约定（`PLANS.md` 文件，*第 3 章* 的规划方法）而非一等规格对象达到类似目的。

#### 并行编排代理

**并行编排代理** 押注于不同策略：它们不采用单一深度推理链，而是扇出至由路由器协调的多个子代理，有时在人类看到任何内容之前，对相互竞争的输出进行评分。对于存在多种合理实现的探索性工作，广度优先探索能浮现单个代理永远不会尝试的选项。权衡在于控制力和可验证性：单次高质量代理遍历产生更清晰的记录，且对明确指定的工单更具成本效益；该类别中新进入者的自我报告基准数据并不总能经受住独立评估。

请谨慎对待任何供应商的自我报告基准数字，直到出现独立评估。使用不同脚手架测量的分数，或由第三方（如独立评估实验室）测量的分数，往往远低于标题数字。脚手架视角双向起作用：包裹在弱公共脚手架中的强模型可能表现不及其自身营销。

### IDE 代理

IDE 代理将 AI 能力直接嵌入编辑器。主要优势是工作流连续性：开发者以可视化差异形式查看建议变更，内联接受或拒绝，永不离开编辑上下文。

#### Cursor

**Cursor** 是主导的 IDE 代理，也是该类别做得最好的最清晰示例。^[²⁴³] 其市场地位反映了真实的用户体验质量而非营销：可视化差异在任何变更被接受前落地，完整的编辑器扩展生态系统保持完好，且无需上下文切换到终端。当你希望在代理接触代码前准确看到其将做什么，且工作流以编辑器为中心时，它具有决定性优势。

权衡是 Token 成本：更丰富的可视化脚手架（编辑器状态、打开文件上下文、内联差异流）消耗比无头代理更多的 Token 完成相同任务，独立测试测量 CLI 代理完成相同工作所用 Token 比 IDE 代理少几倍。^[²⁴⁴] `Cursor` 不是 CLI 代理；对于终端优先工作流（CI/CD 流水线、脚本自动化、无头操作），它在架构上不适合该工作，正如无头代理不适合想要每次编辑都有内联差异的人一样。

#### GitHub Copilot

**GitHub Copilot** 拥有市场上最高的品牌知名度，最初作为自动补全，现已成为具有交互、异步和 CLI 模式的多组件平台。^[²⁴⁵] 两点使其独特。第一是其异步编码代理：你分配一个议题，它启动托管 CI 沙箱，将提交推送到草稿拉取请求，并在完成时请求审查，全程无需你守在桌前。这种委托即遗忘模型在结构上不同于 `Codex CLI` 和 `Claude Code` 使用的交互循环，且真正适合议题分类和直接的错误修复。第二是模型灵活性：`Copilot` 允许你按任务从多个供应商中选择模型，这是单一供应商工具不具备的优势。其弱点是原始代理能力，落后于前沿 CLI 代理；其强项是生态集成，对于已在 GitHub 上的团队，增加代理能力的边际成本极低。

#### 编辑器作为多代理界面

IDE 层级更有趣的发展不是任何单一代理，而是编辑器成为同时托管多个代理的宿主。一些编辑器现在在一个窗口中以对等方式运行多个代理，每个代理在自己的线程中处理代码库的不同部分，通过开放的代理到编辑器协议协调，使任何兼容代理（包括 `Codex CLI`）成为一等公民。在这样的编辑器中运行 `Codex CLI` 赋予你原始终端无法提供的三样东西：共享文件上下文（编辑器转发你的工作目录和打开文件，无需手动 `@` 提及体操）、并行编排（多个 `Codex` 线程与其他代理并行）和统一审批界面（工具执行在编辑器中显示为交互式审批，而非争夺单个终端窗格）。

主流编辑器现在在单个侧边栏中将 `Codex`、`Claude` 和 `Copilot` 作为对等代理呈现，具有本地、后台和云执行模式，体现了相同的融合趋势。对 `Codex CLI` 用户的实际收益是配置可移植性：编辑器集成封装相同引擎并读取相同的 `~/.codex/config.toml`，因此你现有的配置文件、模型偏好和权限设置跨环境保持不变。你在 CLI 配置上的投入在迁移到编辑器托管工作流时不会搁浅；它是同一个脚手架，只是呈现方式不同。

### 融合层

在竞争表象下，工具正在汇聚到一小组共享标准，这比任何单一基准都重要，因为它决定了你被锁定的程度。三个标准现已跨越工具边界：

1.  `AGENTS.md` 作为可移植指令文件。配置 `Codex CLI` 的相同项目指导（*第 4 章*）被越来越多的竞争代理原生读取，因此单个文件无需重复即可塑造多个工具的行为。

2.  **Agent Skills** 作为可移植能力包。`SKILL.md` 目录（*第 10 章*）日益被跨代理识别，因此编写一次的技能可从多个工具调用。

3.  **MCP** 作为可移植工具层。模型上下文协议服务器（*第 8 章*）向任何支持 MCP 的代理暴露相同工具，因此你构建的集成不绑定单一供应商。




对于买方而言，收敛是本章最好的消息。这意味着决策很少是非此即彼的：一个 `AGENTS.md` 文件、一个技能目录和一个 MCP 服务器配置可以在你技术栈中的各个工具间共享，这使得组装和变更多工具工作流的成本都很低。锁定效应正好在原本危害最大的层面上消退。

### 从 Claude Code 迁移到 Codex CLI

由于收敛层标准可跨工具通用，从 Claude Code 切换到 Codex CLI 主要是一项机械性的配置工作，而非重写。像对待任何迁移一样对待它：制定计划、增量执行、每一步都验证。需要迁移五个组件。

#### 指令文件：从 CLAUDE.md 到 AGENTS.md

`AGENTS.md` 是由 Linux 基金会的 Agentic AI 基金会管理的开放标准。^(²⁴⁶) `CLAUDE.md` 专用于 Claude Code。不要删除 `CLAUDE.md`；要重构它。

将通用约定（代码风格、构建命令、测试运行器调用、架构说明）移入 `AGENTS.md`。保留 `CLAUDE.md` 用于 Claude 特有的指令：钩子引用、子代理定义、记忆配置。添加交叉引用：`See @AGENTS.md for build commands, architecture, and conventions.`

如果你无法维护两个文件，可配置 Codex CLI 将 `CLAUDE.md` 作为回退选项：

```
##### ~/.codex/config.toml
project_doc_fallback_filenames = ["CLAUDE.md", "COPILOT.md"]
project_doc_max_bytes = 65536
```

撰写本文时，Codex 会按顺序从仓库根目录向下检查到你的工作目录中的每个目录：`AGENTS.override.md`（将替换同级的任何 `AGENTS.md`） → `AGENTS.md` → `project_doc_fallback_filenames` 中的任意名称。默认字节限制 `project_doc_max_bytes` 为 32 KiB (32768 字节)，适用于整个拼接链；对于大型单体仓库，将其提高至 65536。

#### 技能

技能具有最高的对等性。`SKILL.md` 格式遵循 Agent Skills 开放标准；相同的文件可在 Claude Code、Codex CLI、Cursor 和 Gemini CLI 间通用。Claude Code 将技能存储在 `.claude/skills/<name>/SKILL.md` 下；Codex CLI 从 `.agents/skills/` 加载。目录名称不同；文件格式相同。

将 `.claude/skills/` 复制到 `.agents/skills/`。仅使用 `name`、`description`、`allowed-tools` 和 `disable-model-invocation` 的技能无需更改即可工作。单独审核其他前置元数据键。`context: fork` 键（在隔离的子代理中运行技能）是 Claude Code 的扩展；在依赖它之前请验证 Codex CLI 的支持情况。

#### 子代理

子代理代表了最大的架构分歧。Claude Code 子代理定义为 Markdown 文件，支持交互式编排，父代理可实时查看推理并干预。Codex CLI 子代理定义为 TOML，适合并行批处理工作负载，即分发任务并收集结果。

将每个子代理重写为 `.codex/agents/`（项目级）或 `~/.codex/agents/`（个人级）下的 TOML 代理定义。在 `.codex/config.toml` 中启用 `features.multi_agent = true` 以开启多代理工作流。`agents.max_depth` 默认为 `1`，因此子代理无法在未显式配置的情况下生成更深层的子代理。Codex CLI 子代理每次运行消耗的 token 比等效的单代理运行更多；请在成本对比中考虑此因素。

#### 钩子

撰写本文时，Claude Code 通过 stdin/stdout 上的 JSON 协议提供了二十多种生命周期钩子事件类型。撰写本文时，Codex CLI 支持十种钩子事件：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PreL1-Bullet`、`PostL1-Bullet`、`SubagentStart`、`SubagentStop` 和 `Stop`。与 Claude Code 迁移最相关的五种是 `SessionStart`、`PreToolUse`、`PostToolUse`、`UserPromptSubmit` 和 `Stop`。在 `~/.codex/hooks.json`（或项目级的 `.codex/hooks.json`）的 JSON 文件中配置钩子。钩子默认启用；`config.toml` 中 `[features]` 下的 `hooks` 开关可让你禁用它们（托管配置可固定该设置）：

```
{
 "hooks": {
 "SessionStart": [
 {
 "hooks": [
 { "type": "command", "command": "~/.codex/hooks/on-session-start.sh", "timeout": 15 }
 ]
 }
 ],
 "Stop": [
 {
 "hooks": [
 { "type": "command", "command": "~/.codex/hooks/on-stop.sh", "timeout": 10 }
 ]
 }
 ],
 "UserPromptSubmit": [
 {
 "hooks": [
 { "type": "command", "command": "~/.codex/hooks/on-prompt.sh", "timeout": 5 }
 ]
 }
 ],
 "PreToolUse": [
 {
 "matcher": "Bash",
 "hooks": [
 { "type": "command", "command": "~/.codex/hooks/pre-tool.sh", "timeout": 5 }
 ]
 }
 ],
 "PostToolUse": [
 {
 "matcher": "Bash",
 "hooks": [
 { "type": "command", "command": "~/.codex/hooks/post-tool.sh", "timeout": 10 }
 ]
 }
 ]
 }
}
```

`matcher` 字段是应用于工具名称的正则表达式。撰写本文时，`PreToolUse` 和 `PostToolUse` 匹配 `Bash`、文件编辑工具 `apply_patch` 以及 MCP 工具名称（如 `mcp__filesystem__read_file`）。使用 `"matcher": "Bash"` 直接移植拦截 shell 命令的 Claude Code `PreToolUse` 钩子。对于拦截文件编辑的钩子，使用 `"matcher": "apply_patch"` 进行匹配。

对于副作用钩子（日志记录、Slack 通知、审计跟踪），使用 `Stop` 和 `SessionStart`。按名称拦截文件写入工具的 Claude Code 钩子无法映射到同名的 Codex CLI 工具；改为匹配 `apply_patch`，或通过 `sandbox_mode` 或 `AGENTS.md` 指令强制执行文件写入策略。

#### 配置

Claude Code 使用五层 JSON 级联，其中激活层是隐式的。Codex CLI 使用命名配置文件，因此你始终知道哪个配置处于激活状态，因为是你选择的。每个配置文件位于各自的文件中，`~/.codex/<name>.config.toml`，采用顶层键而非 `config.toml` 内部的 `[profiles.<name>]` 表。运行 `codex --profile <name>` 会先加载 `~/.codex/config.toml`，然后在其之上叠加配置文件：

```
##### ~/.codex/config.toml
model = "gpt-5.5"
model_reasoning_effort = "medium"
approval_policy = "untrusted"
##### ~/.codex/strict.config.toml
model_reasoning_effort = "high"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
##### ~/.codex/fast.config.toml
model = "gpt-5.4-mini"
model_reasoning_effort = "low"
approval_policy = "never"
sandbox_mode = "read-only"
```

在 CLI 处切换配置文件：`codex --profile strict "review the auth module"` 加载基础 `config.toml` 然后叠加 `strict.config.toml`。两个工具的模型命名不同：Claude Code 使用 Anthropic 模型名称（`claude-opus-4-8`、`claude-sonnet-4-6`）；Codex CLI 使用 OpenAI 模型名称。模型名称频繁变更，因此在 CI 流水线中硬编码之前，请根据 OpenAI 文档核对当前名称。

推荐的迁移后布局在仓库根目录并存保留 `AGENTS.md` 和 `CLAUDE.md`，将子代理定义作为 TOML 文件置于 `.codex/agents/`（项目级）或 `~/.codex/agents/`（个人级），并将 `.agents/skills/` 作为两个工具共同读取的共享技能目录。

### 跨代理迁移工具

收敛层使得在任意两个代理之间移植变得主要是机械性的，而不仅限于从 Claude Code 到 Codex CLI。大多数团队的配置、技能、MCP 服务器和会话历史分散在多个框架中；两种机制将这种碎片化变成了已解决的问题。

#### Detect/Import API

Codex CLI 为碎片化提供了一流的解决方案：`externalAgentConfig/detect` 和 `externalAgentConfig/import` JSON-RPC API，由异步后台会话导入提供支持。

`externalAgentConfig/detect` 扫描文件系统以查找其他代理框架可导入的工件。它接受 `includeHome`（扫描主目录中的全局配置）和 `cwds`（要扫描的项目目录），并返回类型化的 `migrationItems`：

| **项目类型** | **涵盖内容** |
| --- | --- |
| `AGENTS_MD` | CLAUDE.md、.cursorrules 或其他可映射到 AGENTS.md 的指令文件 |





| --- | --- |

| `CONFIG` || 全局配置（模型默认值、批准模式、提供商密钥） |

| `SKILLS` || 包含 `SKILL.md` 文件的技能目录 |

| `PLUGINS` || 应用商店插件引用 |

| `MCP_SERVER_CONFIG` || MCP 服务器连接定义 |

检测过程**幂等且增量**：如果 `AGENTS.md` 已存在且非空，Codex 会跳过 `AGENTS_MD`；技能导入不会覆盖现有的技能目录。

`externalAgentConfig/import` 应用选定的迁移项。它会立即返回并在后台异步处理导入，完成后发出 `externalAgentConfig/import/completed` 通知。会话历史记录导入是最繁重的操作，完全在后台通过串行化处理运行以防止重复。

**表 26-2. 常见源 Agent 的具体文件映射**

| **制品** || **Claude Code** || **Cursor** || **Codex CLI 目标** |

| --- | --- | --- | --- |

| Agent 指令 || `CLAUDE.md` || `.cursor/rules/*.mdc` || `AGENTS.md` |

| --- | --- | --- | --- |

| 技能 || `.claude/skills/<n>/SKILL.md` || `.cursor/skills/` || `.agents/skills/` |

| MCP 服务器 || `.mcp.json` || `.cursor/mcp.json` || `config.toml` `[mcp_servers]` |

| 全局配置 || `~/.claude/settings.json` || `~/.cursor/settings.json` || `~/.codex/config.toml` |

对于并行运行多个 Agent 的团队，同步方法通常比一次性迁移效果更好。维护单一事实来源文件（通常为 `AGENTS.md`），并使用构建脚本生成特定工具的变体。

#### Microsoft APM：跨 Agent 配置管理

Microsoft 的 **Agent Package Manager (APM)** 以 MIT 许可证作为开源发布，引入了一个位于任何单个工具之上的配置管理层。^(²⁴⁷) APM 支持八款 AI 编码 Agent（GitHub Copilot、Claude Code、Cursor、OpenCode、Codex CLI、Gemini CLI、Windsurf 和 Kiro），均通过单一清单文件管理。

APM 的 `apm.yml` 在 Node 项目中的角色相当于 `package.json`：即 Agent 所需一切的声明式规范：

```
name: subscriptions-api
version: 1.0.0
dependencies:
 apm:
 - acme/agent-skills/skills/migration-auditor
 - acme/agent-skills/plugins/release-notes
 mcp:
 - name: io.github.github/github-mcp-server
 transport: http
```

运行 `apm install` 可从任意 Git 托管平台解析依赖，并将其部署到各 Agent 的正确位置。`apm.lock.yaml` 文件固定已解析的来源和内容哈希，确保确定性复现。APM 将 Codex CLI 列为其支持的八款 Agent 之一；编译目标名称记录在 APM README 中。

APM 对 Codex CLI 团队的当前价值主要体现在三个方面：跨仓库标准化 `AGENTS.md` 内容（APM 解析传递指令依赖）、分发技能，以及同时使用 Codex CLI、Claude Code 或 Copilot 的团队的跨 Agent 一致性。安全特性包括安装时的内容扫描（阻止用于提示词注入的隐藏 Unicode 字符）、通过内容哈希实现的锁文件完整性，以及通过 `apm audit` 进行的偏移检测。

对于企业团队，`apm-policy.yml` 采用“仅收紧”继承模型强制执行组织对 Agent 配置的约束：企业策略限制最严，仓库策略只能进一步收紧。这补充了 Codex CLI 的 `requirements.toml` 强制执行：APM 控制配置供应链，权限配置文件控制运行时沙箱。

Codex CLI 支持通过可流式 HTTP 连接远程 MCP 服务器（配置服务器 `url` 加上持有者令牌或 OAuth 认证）。一些跨 Agent 包管理器仍保留着过时的假设，即认为 Codex CLI 不支持此功能，并可能跳过 `transport: http` 依赖的 Codex 目标；请查看你的包管理器发行说明，因为这一差距正在缩小。

#### Gemini CLI 停止维护

Google 在 2026 年 I/O 大会上宣布，Gemini CLI 将于 2026 年 6 月 18 日停止维护，由 Antigravity CLI 取代。^(²⁴⁸) 目前正在使用 Gemini CLI 的团队应在截止日期前将其配置迁移至 Antigravity CLI 或 Codex CLI。映射关系简单直接：`.gemini/` 配置映射到 `~/.codex/config.toml`，`.gemini/agents/` 自定义 Agent YAML 文件映射到 `.codex/agents/` TOML 文件，`@agent` 调用映射到 Codex CLI 中的 `/agent`。MCP 服务器配置协议兼容，仅需移动配置文件即可。

### 多工具模式

大多数对比文章的错误前提在于：你必须选择一种工具并坚持使用。资深从业者实际采用的模式是分层栈，每种工具分配到其架构优势所在：

1.  **IDE Agent** 用于交互式开发：编写功能、探索陌生代码、在视觉反馈至关重要的场景下进行结对编程。

2.  **CLI Agent** 用于自动化：CI/CD 任务、批量重构、测试生成，以及任何需要内核级隔离的工作。

3.  **第二个 CLI Agent 或云 Agent** 用于处理第一个 Agent 最不擅长的工作：复杂推理、可编程策略执行，或无需本地会话的长时间运行异步任务。

这些工具通过 Git 共享同一代码库，通过上述汇聚层共享同一上下文，因此开发者按任务而非平台忠诚度来选择工具。边界通常很清晰。编辑单个文件并希望在落地前查看差异，属于 IDE Agent 的工作。涉及文件系统操作、执行测试且需要隔离的多步骤任务，属于 CLI Agent 的工作。委派任务然后离开，属于异步 Agent 的工作。为单行补全使用功能齐全的终端 Agent 属于过度设计；为需要内核沙箱的多步骤 CI 任务使用 IDE 插件则属于设计不足。

有一种从业者变体值得强调，因为它能提升质量而不仅仅是路由工作：**双工具审查工作流**，即一个 Agent 构建，另一个不同的 Agent 审计。^(²⁴⁹) 在一个记录在案的例子中，一个 CLI Agent 负责 Web 应用的初始开发，第二个 Agent 的审查环节发现了第一个遗漏的约二十个 Bug：时间戳错误、导航故障，以及构建者模型盲区中的边缘情况。原则很简单：绝不发布仅有一个模型见过的代码。不同模型有不同的盲区，因此让第二个 Agent 阅读第一个 Agent 的差异，是一种廉价有效的检查，单模型无法复制。这与 *第 20 章* 中对抗性审查模式背后的直觉一致，只是应用在工具间而非工具内。

相关的一个发展是**桌面封装器**的兴起，它们将多个 CLI Agent（Codex CLI 和竞品）集成到一个应用中，具备任务调度、Git 工作树管理 (*第 13 章*) 和远程操作功能。这些工具竞争的是“开发者工作台”——即你整天保持打开的应用——而非底层的 Agent 引擎。底层的 Codex 引擎保持不变；价值主张在于顶层的编排层。该层是否值得采用，取决于其调度和工作区管理是否优于你通过 `codex exec` 加上操作系统级工具所能组装出的方案。对许多团队而言，目前尚不具备优势，但这一品类值得关注。

#### 何时坚持使用现有工具




工具切换有真实成本：学习曲线、配置迁移、团队对齐。仅当架构权衡能证明其合理性时才切换。如果你目前使用其他工具很高效，那么引入 Codex CLI 的理由仅基于特定条件：你需要内核级沙箱而非基于钩子的策略；你运行任务的规模使得 Token 效率差距成为真实成本因素；你的工作流高度面向终端自动化；或你需要大上下文窗口的正式版而非预览版。如果这些条件均不适用，你当前的工具就很好，本书对 Codex 特定配置的深度探讨对你而言只是学术性的而非操作性的。同理：如果你更喜欢待在编辑器中，在代码落地前查看差异，且极少进行终端自动化，IDE Agent 将比任何 CLI Agent 更适合你，终端优先的热情不应凌驾于你自己的工作流偏好之上。如果你当前的工具能很好地处理 80% 的用例，请优化剩下的 20%，而不是替换整个技术栈。

如果你首次向团队引入 Agentic 工具，请从一个工具针对一个定义明确的任务类型开始，然后再扩展。一支自信地使用 IDE Agent 进行内联编辑、刻意使用 Codex CLI 处理 CI 任务的团队，将比安装了五个工具却无使用约定的团队交付得更可靠。

### 沙箱全景

沙箱是工具间架构上最显著的差异因素，因为它决定了当（而非是否） Agent 收到恶意或错误指令时能做什么。按执行强度分层，方法分为清晰的梯队。

| **方法** | **执行层** | **绕过风险** |
| --- | --- | --- |
| 内核级（Seatbelt、Landlock、bubblewrap、seccomp） | 操作系统系统调用层 | 极低：需要内核漏洞利用 |
| 容器级（Docker、Firecracker、每 Agent 一个容器） | 命名空间隔离 | 低：需要容器逃逸 |
| 虚拟机级（云沙箱） | 完整机器隔离 | 极低，但开销较高 |
| 应用层（基于信任、策略文件） | Agent 自我执行 | 中等：提示词注入可绕过 |
| 无 | 无限制 | 高：任何工具调用均不加检查地通过 |

应用此表时有两点细化很重要。首先，现在有多个 CLI 工具将 Shell 子进程的内核级沙箱与用于文件编辑的应用层权限层结合在一起，因此“应用层”行描述的是一个类别，而非某个特定工具。**按工具最弱的执行边界分类，而非最强的。** 一个工具如果对 Bash 实施内核沙箱，却让文件编辑通过自我执行的权限检查，从威胁建模角度来看，它仅与该权限检查对抗提示词注入的能力一样强。

其次，梯队在隔离强度与开销之间权衡。像 Seatbelt 和 Landlock 这样的内核级原语由操作系统以近乎零开销强制执行，且在 Codex CLI 中是内置而非外挂的。容器级隔离为并发 Agent 之间提供更强的分离，代价是容器启动延迟，当你并行运行多个 Agent 并需要其工作树之间有硬边界时，这笔开销值得付出（第 13 章）。虚拟机级隔离被云执行面使用，在最高开销下提供完整机器分离，是完全自主、不受信执行的正确梯队。对于安全敏感环境，内核级或容器级沙箱是不可商量的；对于受信的本地开发，应用层模型可能足够。决策权在于你的威胁模型，而非基准测试，第 16 章将演示如何做出决策。

### 总结

1.  **单一架构轴线划分市场。** Agentic 编码市场沿 CLI 与 IDE 这条线划分，各自针对不同工作流优化：一边是无人值守执行与可脚本化，另一边是紧凑反馈循环与可视化差异。将具名工具视为这些类别的代表，因为类别比品牌更持久。

2.  **编排层比模型更具差异化。** 接口、机制、扩展这三层解释了运行可比模型的工具之间的大部分差异，这正是第 27 章将全面展开的论点。模型决定上限；编排层决定你能触及多少上限。

3.  **CLI Agent 在自动化上胜出。** 它们擅长 CI/CD、内核级沙箱和 Token 效率，因为无头终端操作避免了 IDE 协议层的开销。Codex CLI 的优势集中在机制层，正是调查预测持久差异存在之处。

4.  **Claude Code 是最接近的同辈。** 它在推理质量和可编程钩子表达力上领先；Codex CLI 在 Token 效率和默认内核级隔离上领先。二者是真正的权衡，而非排名，诚实的评估方式是在两者中运行相同任务并对比 Token 计数。

5.  **IDE Agent 在交互式工作上胜出。** Cursor 等工具擅长可视化差异审查和工作流连续性；GitHub Copilot 增加了独特的委托并离线的异步模型及每任务模型选择。两者为相同编辑付出的 Token 成本都比无头 Agent 高。

6.  **融合层降低了赌注。** `AGENTS.md`、Agent Skills 和 MCP 现已跨工具流通，因此多工具栈组装廉价且切换廉价。在最可能造成伤害的层面上，锁定效应正在消退。

7.  **多工具模式优于忠诚度。** 根据架构优势分配每个工具，而非强迫一个工具覆盖所有场景。双工具审查工作流——用一个 Agent 构建，用另一个 Agent 审计——能捕获单模型单次通过遗漏的 Bug，理由正如对抗性审查在单工具内生效一样。

8.  **沙箱是最尖锐的差异因素。** 系统调用层的内核级强制执行，在范畴上不同于 Agent 对自我执行、且可被提示词注入绕过的应用层策略。按工具最弱的执行边界分类，而非最强的。

9.  **仅当权衡证明成本合理时才切换。** 学习曲线、配置迁移、团队对齐是真实的；如果你当前的工具能处理好 80% 的用例，请优化剩下的 20%，而不是替换整个技术栈。

10. **切换工具主要是机械操作。** 因为 `AGENTS.md`、Skills 和 MCP 跨 Agent 流通，从 Claude Code 迁移到 Codex CLI 是一个五组件配置练习（指令、技能、子 Agent、钩子、配置），加上 `externalAgentConfig` 检测/导入 API 及微软 APM 等跨 Agent 包管理器自动完成其余工作。
