# 第一章：什么是 Codex CLI？

在配置任何 Profile、编写 `AGENTS.md` 文件或运行首个任务之前，了解 `Codex CLI` 的来龙去脉及其解决的问题会有所帮助。本章追溯从最初的 OpenAI Codex 模型、到 GitHub Copilot 的自动补全时代、再到 2023 和 2024 年向代理的转变、以及造就今日 `Codex CLI` 的设计决策的脉络。该工具是一个终端优先、沙箱化、开源的编码代理，它读取你的仓库、运行你的测试、进行提交，并遵循纯 Markdown 文件中的项目专用指令。

读完本章，你将拥有本书其余部分赖以构建的心智模型。

### 学习目标

你将能够：

1.  向同事或团队负责人解释自动补全、基于聊天和代理式 AI 编码辅助的区别
2.  在当前工具全景图上定位 `Codex CLI`，理解其与 Claude Code、Cursor、GitHub Copilot、Cline 及云托管代理的区别
3.  清楚阐述定义 `Codex CLI` 核心价值主张的四大能力：读取仓库、运行测试、进行提交和遵循 `AGENTS.md`

### Codex 之前：简史

“Codex” 这个名字比 CLI 工具早四年。要理解 `Codex CLI` 是什么，你需要了解它之前发生了什么。

#### Codex 模型（2021）

2021 年 7 月，OpenAI 发布了一篇研究论文（arXiv:2107.03374），由 Mark Chen 等人撰写，描述了一系列在 GitHub 公开代码上微调的 GPT 语言模型。^[3] 最大变体单独在 159 GB Python 代码上训练。论文表明，一个足够大的模型，在足够多代码上微调，仅凭文档字符串描述就能解决非平凡比例的竞技编程问题，无需工具、测试运行器或检索系统。




团队还推出了 `HumanEval`，这是一个包含 164 道手写编程问题的基准测试，每个问题均由函数签名和文档字符串定义。如果模型能在一次尝试中生成正确的实现，即视为通过。最初的 `Codex` 模型通过率为 28.8%。这个数字在今天看来只是个历史趣闻，但在 2021 年，它证明了将语言模型规模应用于代码能产生质变的新能力。^(⁴)

最初模型的两个特性塑造了后续的一切发展。首先，它是生成式的，根据提示逐个 token 生成代码，这意味着它能补全部分函数、在语言之间转换，并用自然语言解释自己的输出。其次，它围绕补全隐喻进行优化：你给它文档字符串，它返回实现。这种交互模式定义了 AI 辅助编程的第一个商业化时代。

#### GitHub Copilot 与自动补全范式 (2021 年 6 月)

2021 年 6 月 29 日，GitHub 推出了 `GitHub Copilot` 技术预览版，由 `Codex` 模型驱动。[⁵] 交互体验优雅：随着你输入，幽灵文本随之出现。按 `Tab` 接受；继续输入即忽略。模型拥有足够上下文——打开的文件、函数名、周围代码和文档字符串——能足够频繁地生成有用的补全，让人真切感受到帮助。

`Copilot` 的传播速度超过几乎所有此前的开发者工具。^(⁶) 自动补全范式——AI 看着你的肩膀帮你把话说完——已然来临。

这种范式内嵌的局限性，从内部并不明显。自动补全是被动且局部的：模型看到你输入的内容并预测接下来的内容。它不读取你的测试套件、不理解你的构建系统、也不在乎其建议能否通过你的 linter 检查。它只是补全代码行。对于样板代码和熟知的模式，这通常足够。但对于任何需要多文件推理、迭代测试反馈或架构约束满足的场景，自动补全触及到了硬性上限。

#### ChatGPT 的转变 (2022 年 11 月)

在专用 `Codex` API 模型于 2023 年 3 月弃用之前，一个更重大的事件重塑了开发者实践。`ChatGPT` 于 2022 年 11 月 30 日发布。^(⁷) 五天内用户破百万；两个月内破亿，成为当时有记录以来增长最快的消费级应用。

对开发者而言，`ChatGPT` 将交互模式从行补全变为对话。你描述问题、收到回复、追问、迭代。反馈回路比 Tab 补全慢，但处理复杂问题的能力显著增强。你可以粘贴堆栈跟踪、请求解释、要求修复、询问修复原理并索要变体，全在一个线程内完成。

`ChatGPT` 并非为编码工具而设计，但它揭示了自动补全范式掩盖的事实：模型具备多步推理、约束应用和任务分解能力。它只需要一个允许对话跨越多轮交互的界面。基于聊天的编码辅助时代由此开启，并将持续到下一次范式转移：代理。

### 自动补全的问题

自动补全范式存在结构性局限，无论模型如何改进都无法完全解决。理解这一点，就能明白为何随后出现的代理工具不仅仅是“更好的自动补全”，而是完全不同的事物。

自动补全在单一时刻作用于单一上下文窗口。模型看到你打开的代码，提出补全建议，然后停止。它无法运行你的测试、观察失败并修正建议。无法打开第二个文件以检查与别处定义的类型定义是否一致。无法读取你的 CI 日志以理解构建为何中断。

这不是模型能力问题，而是界面问题。一个足以推理多文件系统和迭代测试反馈的复杂模型，若界面只允许它在单一时刻看到单个文件并产出单次补全，便无法施展这些能力。

从自动补全转向聊天有所帮助，因为聊天界面允许多轮推理。但聊天仍需人工复制粘贴错误信息、获取相关文件内容、传递测试结果。人类在模型与开发环境间搭桥。这增加了摩擦，限制了模型在单次会话中能完成的工作量。

代理模式消除了这座桥。你不再传递信息，而是赋予模型直接访问环境的工具：读取此文件、运行此命令、写入此输出并提交此变更。模型随即能端到端完成多步任务：读取失败测试、定位实现、修复 Bug、再次运行测试、若通过则提交，全程无需人工在每步中转。

在此语境下，“代理”意味着什么？模型拥有代理权：在真实环境中采取行动的能力，而非仅建议文本供人类执行。代理工具在单次会话中读取文件、执行 Shell 命令、观察输出并决定下一步。人类设定目标；代理追踪目标。

“代理”不等于“完全自主无监管”。`Codex CLI` 支持多种审批模式，包括在任何写入或命令执行前需用户确认的交互模式。代理模式赋予模型访问环境的能力；并未将人类监督移出循环。

### 代理格局

你大概率已接触过多款 AI 编码工具：在编辑器里、会议演讲中、招聘广告里、同事工作流中。如今大多数专业开发者同时使用多款 AI 工具。^(⁸) 这非赢家通吃的市场，而是分品类的市场，理解品类对于理解 `Codex CLI` 的定位至关重要。

格局按代理驻留位置分为三类：编辑器内、终端内、云端。

#### 类别 1：IDE 集成代理

这些工具在开发者最常驻足的地方相遇：代码编辑器内。IDE 代表集成开发环境，即内置运行、测试、调试工具的代码编辑器。`Visual Studio Code` (`VS Code`) 是当今专业开发者中最流行的 IDE。

`GitHub Copilot` 仍是部署最广、认知度最高、职场采用率最高的 AI 编码工具。^(⁹) `Copilot` 起步于自动补全（幽灵文本，Tab 接受），现已发展为更宽泛的平台：用于对话式辅助的 `Copilot Chat`、通过拉取请求进行异步任务完成的 `Copilot Coding Agent`，以及扩展生态。对企业而言，`Copilot` 与 GitHub 的集成——代码、拉取请求、CI 均驻留于此——赋予了其纯产品对比常低估的结构性优势。

由 Anysphere 开发的 `Cursor` 是主导级 IDE 集成代理之一。^(¹⁰) Anysphere 未选择构建扩展，而是 fork 了 `VS Code` 并将 AI 嵌入每个表面：通过 `Composer` 实现多文件编辑、通过 `Background Agents` 实现并行自主会话、通过深度代码库索引赋予模型比提示词注入更丰富的结构上下文。`Cursor` 面向愿留在编辑器内的开发者。其可视化差异、行内接受/拒绝工作流、熟悉的扩展生态，适合那些希望在变更落地前精确查看代理动作的人群。它非终端原生，亦非开源。




# AI 编码工具全景

## 类别 1：IDE 智能体

**Cline**（最初名为 Claude-Dev）是一个开源的 VS Code 扩展，它赋予模型工具访问权限、文件读取、Shell 执行以及通过 Playwright 进行浏览器控制的能力，并允许其在编辑器内规划并执行多步骤任务。^(¹¹) 与 Cursor 不同，它运行在标准的 VS Code 中，而不是一个分支版本，因此你可以保留完整的扩展生态系统。Cline 与模型无关，并由贡献者社区积极维护。

#### 类别 2：终端智能体

终端智能体运行在 Shell 中，即你输入命令并查看其输出的基于文本的界面。自图形界面出现之前，这就是开发人员与计算机交互的方式，它至今仍是专业软件开发的基石。

终端智能体可与 Unix 工具组合使用，自然地集成到 CI/CD 流水线（自动构建、测试和部署代码的系统）中，并能在任何拥有终端的环境中工作：SSH 会话、Docker 容器和无头服务器。Codex CLI 就属于这一类别。

**Claude Code** 由 Anthropic 于 2025 年 5 月发布，是 Codex CLI 最直接的竞争对手，也是你最有可能与其并列遇到的工具。^(¹²)

Claude Code 以终端为先、具备智能体特性，并使用一个名为 `CLAUDE.md` 的项目指令文件，其功能与 Codex CLI 的 `AGENTS.md` 类似。它运行在沙箱环境中，支持用于并行执行的子智能体和智能体团队，并与 Anthropic 的模型上下文协议 (MCP) 深度集成，MCP 是一种让 AI 工具连接外部服务和数据源的标准。Codex CLI 同样支持 MCP。这两个工具共享足够多的设计理念，以至于技能可以在它们之间迁移。关键差异在于：模型系列（Claude 对比 GPT）、子智能体架构（Claude 使用基于邮箱的智能体团队；Codex CLI 使用带有路径寻址的 TOML 定义子智能体）以及生态系统。

如果你所在的团队使用 Claude Code，或者你正在为工作流评估这两个工具，了解 Claude Code 的设计决策将加深你对 Codex CLI 的理解，反之亦然。*第 26 章*提供了详细对比。

**Aider** 由 Paul Gauthier 于 2023 年创建，是最早的开源终端智能体之一，并影响了后续工具的设计。^(¹³) 其核心创新是结构化编辑格式：Aider 不再让模型流式输出原始代码，而是提示模型生成可确定性应用的 diff 块。Aider 与模型无关（支持 500 多家 LLM 提供商）并保持活跃开发。对于有严格数据驻留要求且需要特定模型提供商的组织，Aider 将界面与模型解耦是一项真正的优势。

#### 类别 3：云端与托管智能体

这些工具在云环境中异步运行，通常集成到拉取请求工作流中。

**GitHub Copilot Coding Agent** 直接连接到 GitHub Issues：你将 Issue 分配给 Copilot，智能体提出计划，在沙箱环境中生成实现，并打开一个草稿拉取请求供审查。^(¹⁴) 该流程是异步的：你委派任务、离开，回来时已有一份拉取请求。这代表了平台所有者的押注：智能体工具的正确位置，是集成在代码已被审查和合并的工作流中。

**Devin** 由 Cognition Labs 于 2024 年 3 月发布，被营销为“首个 AI 软件工程师”，是一个功能齐全的托管自主智能体，拥有浏览器、Shell 和编辑器访问权限，旨在无需人工干预即可在长时间会话中完成工程任务。^(¹⁵)

**Google Jules** 和 **Codex Cloud Tasks**（OpenAI 自身的云产品）代表了“即发即弃”式智能体执行的增长趋势：提交任务，智能体在隔离的云环境中工作，结果就绪时你进行审查。

### 定义 Codex CLI

2025 年 4 月 16 日，OpenAI 发布了 Codex CLI，这是一个由 Fouad Matin 和 Michael Bolin 构建的开源、Apache 2.0 许可的终端智能体。^(¹⁷) 以 AI 发布标准来看，此次发布相当低调。没有“AI 软件工程师”的框架宣传。README 将其描述为一个供希望在终端中工作的开发者使用的工具。

Andrej Karpathy 将 Codex CLI 定义为 Software 3.0 平台：上下文窗口是杠杆，`AGENTS.md` 是程序，而“ harness（约束与验证框架）”，即配置、约束和验证智能体的纪律，正是区分高效使用与混乱的关键。^(¹⁸) 这一框架构成了本书的核心论点。*第 27 章*将对此进行充分展开。

区分 Codex CLI 与其同类工具的设计决策均是深思熟虑的，理解它们是熟练使用该工具的先决条件。

#### 终端优先

Codex CLI 运行在你的 Shell 中。它不是 VS Code 扩展，不是托管的 Web 服务，也不是主要的 GUI 应用程序（尽管存在一个用于管理并行会话的配套 macOS 应用）。

这一点很重要，因为终端工具可与 Unix 生态系统组合：管道、重定向、环境变量、Shell 脚本、Cron 任务和 CI 流水线。任何能运行 Shell 命令的东西都可以调用 Codex CLI，这是*第 15 章*中 CI 集成模式的基础。

#### 无头且可脚本化

`codex exec` 命令以非交互方式运行智能体，接受参数或标准输入中的提示词，并在任务完成时退出。正是这个接口使得 Codex CLI 适用于自动化流水线。GitHub Actions 作业可以像调用 `pytest` 或 `eslint` 一样调用 `codex exec`，作为工作流中的一个步骤，并捕获结构化输出供下游处理。^(¹⁹)

#### 内核层级沙箱

当我们说 Codex CLI 是“沙箱化”的，意味着操作系统在其运行时限制智能体能做什么。在 macOS 上，Codex CLI 使用 Apple Seatbelt 限制文件系统和网络访问。在 Linux 上，它使用 bubblewrap 和 seccomp。这些是内核级安全机制：限制由操作系统强制执行，而非由应用程序执行。智能体无法意外绕过它们，而提示词注入（隐藏在输入文本中的恶意指令）导致模型误以为拥有提升权限，仍会在内核级被阻止。^(²⁰)



你可以通过在 `~/.codex/config.toml` 中定义的审批模式和沙盒配置文件，刻意扩大沙盒范围。但默认情况下是受限的，且该限制是真实存在的。

#### AGENTS.md 感知

Codex CLI 会从你的仓库根目录及子目录读取 `AGENTS.md` 文件，加载特定于项目的指令：运行哪个测试命令、偏好哪个工具链、遵循哪些约定、避开哪些陷阱。^²¹ 该格式现已成为 Linux 基金会旗下 Agentic AI Foundation 维护的开放标准。大多数主流 Agentic 工具均已采用。

*第 4 章* 深入介绍 `AGENTS.md` 的编写方法。

#### Apache 2.0 开源

Codex CLI 的源代码公开托管于 GitHub，并接受社区贡献。对于一个代表你执行 Shell 命令的工具而言，这种透明度是信任模型中极具意义的一环。

### 为什么终端很重要

将 Codex CLI 构建为终端工具，而非 IDE 插件或托管式 Web 应用，这是关于可组合性的宣言，而非对命令行的怀旧偏好。

#### 与 Unix 工具的可组合性

Unix 工具可组合。一个程序的输出成为下一个程序的输入。过滤器、转换器和聚合器链接成管道。Shell 是程序间通过标准输入输出对话的协调层。

身处该环境的智能体，免费继承了这种可组合性。将 Codex CLI 输出管道传给 `jq` 以提取结构化结果。在 Shell 脚本中封装 `codex exec` 并通过 cron 定时夜 ly 运行。在 Makefile 目标中串联多个会话，依次完成构建、测试、修复和提交。传递环境变量以控制行为，无需修改任何配置文件。

这一切都不需要 Codex CLI 提供特殊支持。这仅仅是作为一个读取 stdin、写入 stdout 并返回有意义退出码的终端工具的必然结果。

#### 无需繁文缛节的 CI/CD 集成

CI 流水线本质是 Shell 脚本。GitHub Actions 工作流是描述 Shell 命令的 YAML 文件。Jenkins 作业、CircleCI 流水线和 GitLab CI 配置归根结底都是：按顺序运行这些命令，设置这些环境变量，在该容器中执行。

原生终端工具的智能体，如同任何其他命令行工具一样自然集成。你不需要 GitHub App、OAuth 集成、Webhook 处理器或专用云环境。你只需在密钥存储中配置 API Key，并在工作流文件中调用 `codex exec`。

对于受监管环境或企业防火墙后的团队而言，新服务集成需要安全审查，这一点至关重要。一个使用与你其他 API 调用相同网络路径的 CLI 工具，比新的 SaaS 集成更容易获批。

`codex exec` 命令结合 `--ask-for-approval never` 和限制性沙盒模式（如 `workspace-write` 或 `read-only`），专为 CI 场景设计。*第 15 章* 详细演示了完整的 GitHub Actions 集成模式，包括如何为自动化上下文界定沙盒范围。

#### 无需 GUI

开发环境各异。有的开发者用 VS Code，有的用 Neovim、Emacs 或 Helix。有的通过 SSH 在无法运行 GUI 的远程服务器工作。有的在容器化环境中，安装 Electron 应用不可行。

终端工具适用于所有这些场景。SSH 会话、Docker 容器、远程开发环境和无头 CI 运行器都有 Shell。存在于 Shell 中的智能体，便在 Shell 存在的任何地方可用。

使 Codex CLI 在交互会话中安全运行的沙箱机制在操作系统层面生效，这意味着它在 macOS (Seatbelt) 和 Linux (bubblewrap/seccomp) 上的行为有所不同。如果你在 macOS 上开发，却在 Linux 上部署 CI 自动化，请在依赖生产流水线前，在两个平台上测试你的沙盒配置文件。

### 核心主张

Codex CLI 的核心主张可以用一句话概括：你描述任务，智能体读取你的仓库、运行你的测试、创建提交，并在完成时告知你。

这四项能力将 Codex CLI 与自动补全时代、基于聊天的辅助工具，以及更简单的 Agentic 工具区分开来。

#### 读取整个仓库

智能体不局限于你打开的单个文件。得益于大上下文窗口，大多数项目代码库可装入单个上下文。智能体可同时阅读某文件的类型定义、另一文件的实现模式、第三个文件的测试固件，并在决定如何实现你的需求时统筹推理。

这对重构最为关键，因为一个文件中的正确修改往往取决于分布在几十个其他文件中的使用模式。自动补全看不到这些模式。聊天需要你手动粘贴。Codex CLI 自行发现它们。

#### 运行你的测试

智能体可调用你的测试套件，观察输出，并利用失败信息指导下一步动作。这个反馈循环——写代码、跑测试、观察失败、修正——正是资深开发者的工作方式。Codex CLI 自主参与该循环。

测试运行器在 `AGENTS.md` 中指定，或从仓库结构推断。智能体运行的正是你在终端中会运行的命令。输出被捕获、解析，并融入其下一动作。

#### 创建提交

经你许可，智能体将工作提交至 Git。结果是带有有意义提交信息的、可审查的真实历史，而非编辑器中的未保存更改，也非需复制粘贴的差异。提交是真实的，历史是真实的，你可像审查其他变更一样用 `git log` 或 `git diff` 审查它。

你配置的审批策略和沙盒决定了智能体提交的自主程度。在 `on-request` 策略下，智能体在运行前提议命令和编辑供你批准。`untrusted` 策略更严格，几乎所有操作都升级确认。`never` 策略搭配 `workspace-write` 沙盒，适用于 CI 流水线和可信环境，让智能体无中断地端到端运行。

#### 遵循 AGENTS.md

智能体读取并遵循 `AGENTS.md` 文件中的指令。这些不是提示；它们是智能体视为其运行上下文一部分的约束性指令。若 `AGENTS.md` 指定 `uv` 而非 `pip`，智能体用 `uv`。若指定 `just test` 而非 `pytest`，智能体运行 `just test`。若警告部署脚本中的已知陷阱，智能体会避开。

这是将你团队的制度性知识编码进智能体行为的方式。智能体不知你代码库的历史、团队的决策或组织的惯例，除非你将其写下来。`AGENTS.md` 正是你记录它们的地方。

`AGENTS.md` 的价值随具体程度而增。通用建议（“写整洁代码”）对智能体行为无可衡量影响。具体、非显而易见的工具指令（“用 `uv run pytest` 而非直接用 `pytest`，虚拟环境不会自动激活”）有显著、可靠的效果。*第 4 章* 介绍了 `AGENTS.md` 应包含什么、不应包含什么。

### 总结

1.  **从研究模型到自动补全。** 原始 OpenAI Codex (2021) 证实了代码微调语言模型能从描述生成实现。GitHub Copilot (2021) 将自动补全带给开发者，却也定下了其天花板：被动、局部、无法运行测试或跨文件推理。

2.  **对话与 Agentic 转向。** ChatGPT (2022) 将交互模式转为对话。Agentic 转向 (2023–2024) 赋予模型工具访问权，实现多步自主任务完成。
